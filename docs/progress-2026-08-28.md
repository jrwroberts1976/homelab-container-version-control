# Development checkpoint — 28 August 2026

## Current objective

Do not move on to unrelated infrastructure work until the homelab has a repeatable controlled update path for all actively used container workloads.

The preferred design is:

- one generic update front end rather than service-specific update scripts;
- high-level caller variables only: service, desired application version, target hosts and action;
- reviewed service/host metadata supplies Compose paths, immutable image identities, health checks and rollback data;
- the same approved application version is used across servers wherever upstream architecture support allows it;
- `amd64` and `arm64` may legitimately use different immutable platform digests for the same application version;
- Docker Compose and Kubernetes use different execution backends behind the same estate-level service/version intent.

## Estate update coverage goal

Stage 6 completion requires an inventory/coverage matrix for every active workload, including:

- host;
- service;
- current version;
- desired version;
- platform/architecture;
- immutable image identity;
- update backend;
- health check;
- rollback method;
- tested update status.

Each workload should end in one of four explicit states:

1. generic update path managed and tested;
2. intentionally pinned/manual with documented reason;
3. unsupported pending framework work;
4. obsolete and approved for removal.

The goal is that no important container relies on an ad-hoc `docker pull`/manual recreation procedure.
